# Phase 5BK native backend and worker packaging

Phase 5BK builds two standalone PyInstaller directories on each **target operating system**. Windows x86_64 produces `desktop/dist-native/windows-x86_64/backend/RavenTechBackend.exe` and `desktop/dist-native/windows-x86_64/worker/RavenTechWorker.exe`. Linux x86_64 produces `desktop/dist-native/linux-x86_64/backend/raventech-backend` and `desktop/dist-native/linux-x86_64/worker/raventech-worker`. A Windows build does not produce a Linux binary. The directories remain ignored by Git. Phase 5BL packages the matching OS/architecture directories as Tauri resources or portable sibling resources. Nuitka standalone was attempted first, but dependency analysis consumed several gigabytes of memory and was impractical in the available build environment. PyInstaller standalone is the selected fallback: it supports Python 3.14, includes an interpreter, and keeps migration and report resources inspectable. A single-file executable would make resource loading and startup less predictable.

Build on the target host with the declared backend requirements and `scripts/native/requirements-build.txt` installed in an isolated build environment. From the repository root:

| Windows PowerShell | Linux shell |
| --- | --- |
| `scripts/native/build_native_backend.ps1` | `bash scripts/native/build_native_backend.sh` |
| `scripts/native/build_native_worker.ps1` | `bash scripts/native/build_native_worker.sh` |
| `scripts/native/validate_native_runtime.ps1` | `bash scripts/native/validate_native_runtime.sh` |

The fixed build copies only `backend/alembic`, `backend/app/templates`, and `backend/data/knowledge` into the artifact's read-only `resources` directory. ReportLab, python-docx, python-whois, Chroma, and sentence-transformers have fixed package includes because existing features import them dynamically. No operator `.env`, secrets, reports, uploads, logs, database, or vault are copied. Each component manifest records product, version, build OS/architecture, Git commit, UTC build time, binary SHA-256 and size, PyInstaller version, desktop profile, and external dependencies. The artifact validator checks hashes, version, resource presence, and forbidden files. Dependency resolution is not yet locked to exact hashes; use an isolated, controlled build environment and retain its package inventory for reproducibility.

## Configuration and paths

Run both binaries with `RUNTIME_PROFILE=desktop`. The native launcher selects that profile by default, sets external config path, and never reads configuration from the artifact. Configuration priority is **process environment**, then `%LOCALAPPDATA%\RavenTech OSINT\config\.env` on Windows or `$XDG_CONFIG_HOME/raventech-osint/.env` on Linux, then safe application defaults. When XDG variables are absent, Linux uses `~/.config`, `~/.local/share`, and `~/.local/state`. Mutable reports, logs, and runtime files stay outside the artifact. Windows uses `%LOCALAPPDATA%\RavenTech OSINT\{reports,logs,runtime}`; Linux uses XDG data/state directories. Existing data is not moved. PostgreSQL remains external and required. Configure `DATABASE_URL` for an address reachable from the **host OS**, such as a published loopback port; the Docker Compose hostname `postgres` is valid inside Docker and should remain unchanged there, but it does not resolve for a standalone host executable. Never place a credential-bearing URL in a build artifact or manifest. Migrations must be applied using the established operator Alembic workflow. `--migration-status` reads packaged revision metadata but does not migrate. Redis and Celery are not required in desktop mode. Docker and Python development workflows remain supported.

`RavenTechBackend.exe --version|--check|--migration-status|--serve` and the equivalent Linux executable have fixed options. `--check` validates config, imports, resource availability, and paths without connecting to or changing PostgreSQL. `--serve` binds `127.0.0.1:8000` by default. `--host` accepts only a literal loopback or private IPv4 address and `--port` is bounded; a private-LAN bind is an explicit operator choice. Port collision exits nonzero and never kills another process. `RavenTechWorker.exe --version|--check|--run` and the Linux worker equivalent use the same external config and fixed native handler registry. Ctrl+C stops the worker cooperatively. Backend and worker write separate JSON logs with existing redaction and 2 MB rotating files (three backups each). No firewall rules or autostart are changed.

## Platform parity and current limits

The native launcher forces Hugging Face and Transformers offline mode. Existing optional local embedding features require an already provisioned local model cache; the standalone artifact never downloads model weights at runtime.

The FastAPI routes, PostgreSQL auth/jobs, reports, monitoring and Operations Center are shared code on Windows and Linux. Native Tauri host metrics use Windows APIs or Linux sysinfo. Local process inventory is normalized by the Tauri host provider. On Linux, process identity is rechecked using `/proc/<pid>/stat`; root-owned and unverifiable processes are non-actionable, and an authorized termination requests local SIGTERM. systemd service inventory and narrowly scoped local actions use system D-Bus, with an unavailable state when D-Bus cannot be reached. The manual Linux ServerHost agent reads existing `/proc/net/arp` observations within the host's private /24 and reports only to the authorized backend; it performs no probes. Windows SCM and native host behavior remain in place. Existing authorized LAN TCP observations, endpoint posture, alerts and service analysis use shared backend schemas. Linux-specific behavior must be validated live on Linux; Windows mocks are not evidence of Linux runtime success.

Phase 5BL integrates backend/worker supervision into Tauri. Future work is local PostgreSQL bootstrap (5BM), Docker-optional desktop operation (5BN), Windows and Linux clean-machine acceptance (5BO–5BP), and Knowledge/Obsidian ingestion through the fixed job abstraction (5BQ). Those future phases are not implemented here.

Validation in Phase 5BK used a real Debian x86_64 WSL environment with systemd for Linux ELF, XDG, `/proc`, and system D-Bus checks. WSL live results are reported separately from Windows results and are not clean-machine bare-metal Linux acceptance. Actual clean Linux distribution acceptance remains for a later phase.

## Phase 5BL — Tauri native runtime supervision

Release desktop runs use the cross-platform Tauri supervisor for the fixed PyInstaller backend and worker. The supervisor verifies the RC6 release and native runtime profile, waits for PostgreSQL/migration/storage prerequisites before starting the worker, and reports owned versus external components. It uses bounded restart attempts and cooperative shutdown markers, and only terminates retained child processes that this desktop launched. A per-user Windows mutex or Linux file lock prevents duplicate desktop sessions from independently starting children. Backend port conflicts and external components are observation-only.

Windows portable/installer packages include Windows x86_64 backend and worker resources; Linux x86_64 packaging includes Linux runtime directories. PostgreSQL remains external and required. Redis/Celery are not required for native desktop mode, while Docker and development profiles remain supported. No OS autostart, systemd installation, updater, or automatic downloads are added. See `NATIVE_RUNTIME_SUPERVISOR.md` for ownership and shutdown details. Linux WSL evidence is not clean-machine Linux acceptance.
